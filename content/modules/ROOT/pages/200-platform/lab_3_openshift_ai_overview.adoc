= Lab 1.3 — Publish Qwen3.8 as a Service

Operators are still installing. Understand *why* Models-as-a-Service, wait until the operators are Ready, then apply the serving stack. Developers get one HTTPS front door and one `sk-oai-` key — not a raw predictor Service, and not `api.openai.com`.

====

== Why Models-as-a-Service

OpenShift AI 3.5 serves the model as an `LLMInferenceService`. Models-as-a-Service sits in front: Gateway, API keys, token quota. GitOps still owns the serving stack. The dashboard is the UI for catalog, subscriptions, and extra keys.

image::model-serving-architecture.png[Qwen3.8 as Models-as-a-Service, align="center"]

Anything that already speaks OpenAI works. One key, not an access/secret pair. Do not install Service Mesh 3 — OpenShift 4.22 already has Gateway API.

[cols="1,2", options="header"]
|===
| Compared with a plain Deployment | What MaaS adds

| You wire GPU tolerations and a Route yourself
| Same placement, plus KServe TLS, shm, probes, HTTPRoute on `maas-default-gateway`

| No auth
| `sk-oai-` keys, groups, 429 when over budget

| Generic CPU/memory metrics
| vLLM tokens/s + consumption per key
|===

This instantiates the serving control plane, Dev Spaces, GPU policies, and the MaaS gateway. == Step 2: Publish Qwen3.8 to MaaS

This creates:

* The `llm-serving` namespace and 50 Gi model-cache PVC
* `LLMInferenceService/qwen3` — Red Hat vLLM CUDA 3.5.0 on the GPU node, attached to `maas-default-gateway`
* `MaaSModelRef` (catalog), `MaaSAuthPolicy` (who can call it), `MaaSSubscription` (token quota)

Wait until the GPU node is Ready, then apply:

[source,sh,role=execute]
----
until oc get node -l node.kubernetes.io/instance-type=Standard_NC24ads_A100_v4 \
    --no-headers 2>/dev/null | grep -q .; do
  sleep 10
done
oc wait node -l node.kubernetes.io/instance-type=Standard_NC24ads_A100_v4 \
  --for=condition=Ready --timeout=900s

oc apply -k deploy/inference

=== The LLMInferenceService (after the apply)

[source,yaml]
----
spec:
  replicas: 1
  model:
    uri: hf://RedHatAI/Qwen3.8-27B-INT4
    name: qwen3                          # <1>
  storageInitializer:
    enabled: false                       # <2>
  router:
    gateway:
      refs:
        - name: maas-default-gateway     # <3>
          namespace: openshift-ingress
  template:
    containers:
      - name: main
        image: registry.redhat.io/rhaii/vllm-cuda-rhel9:3.5.0
        args:
          - --served-model-name=qwen3
          - --max-model-len=262144
          - --ssl-certfile=/var/run/kserve/tls/tls.crt   # <4>
----

<1> API model id stays `qwen3`; the display name is Qwen3.8
<2> Weights already live on PVC `qwen-model-cache` (`HF_HOME=/opt/models`). Skip the storage-initializer re-download.
<3> Required for MaaS: the HTTPRoute attaches to `maas-default-gateway`
<4> OpenShift AI 3.5 enables backend TLS by default; vLLM must present the KServe service-CA cert

The image is *Red Hat AI Inference* CUDA (`rhaii/vllm-cuda-rhel9:3.5.0`) — not community `vllm/vllm-openai`.

=== Let the model load in the background

A cold cluster downloads ~18 GiB from Hugging Face into PVC `qwen-model-cache` (`HF_HOME=/opt/models`). If that cache is empty, first Ready can take 10–20 minutes. If weights are already on the PVC, vLLM mainly loads them into GPU memory (~5–8 minutes). Wait in the background for 20 minutes so a cold pull can finish:

[source,sh,role=execute]
----
until oc get llminferenceservice/qwen3 -n llm-serving >/dev/null 2>&1; do sleep 5; done
oc wait llminferenceservice/qwen3 -n llm-serving \
  --for=jsonpath='{.status.conditions[?(@.type=="Ready")].status}'=True \
  --timeout=1200s &
echo "Model wait started in background (PID $!)"
----

== Step 3: Mint the workshop API key

Inference uses *one* `sk-oai-` Bearer token (not an access key + secret). The script mints a key bound to `qwen3-workshop` (5 000 000 tokens / 24h) and stores it as `OPENAI_API_KEY` for every Dev Spaces workspace.

[source,sh,role=execute]
----
bash deploy/inference/mint-workshop-key.sh
----

You have now:

* Dashboard — `https://rh-ai.apps.<apps-domain>/`
* Gateway — `https://maas.<apps-domain>/`
* `LLMInferenceService/qwen3` loading on the GPU
* Catalog, access, quota (`MaaSModelRef` / `MaaSAuthPolicy` / `MaaSSubscription`)
* One `sk-oai-` key in Secret `ai-provider-openai-api-key`

Lab 2.1 smoke-tests the same URL OpenCode will call. Extra keys for curl can also be created in the dashboard; they do not replace this Secret.
