= Lab 1.4 — Publish DeepSeek on Foundry

include::ROOT:partial$pr-preview.adoc[]

== Goal

Deploy DeepSeek on Microsoft Foundry for code generation and agent tool use. Test the provider directly before publishing it through the OpenShift AI gateway; DeepSeek runs on Azure, leaving the T4 for D3.

[NOTE]
====
*Estimated time:* 15 minutes +
*Persona:* Platform Engineer +
*Blocking:* Lab 1.5 reads `state/foundry.env` from this lab. Stay in this shell until the curl returns a sentence.
====

[IMPORTANT]
====
This deployment uses Global Standard, pay-per-token pricing in East US 2. Reasoning tokens count as output. See xref:400-observability/lab_1_llm_metrics.adoc[Lab 3.1] for usage and infrastructure-cost interpretation. An idle coding deployment has no token usage charge; the cluster and GPU workers have separate infrastructure costs.
====

== What you are creating

[cols="1,2", options="header"]
|===
| Setting | Value

| Foundry account
| `arodeepseek<lab-suffix>` in the lab resource group, kind `AIServices`, East US 2

| Deployment
| `deepseekv4pro`

| Model
| `DeepSeek-V4-Pro`, format `DeepSeek`, version `2026-04-23`

| SKU
| `GlobalStandard`, capacity `500` (500 000 tokens/minute)
|===

Act 0 detected the subscription and the resource group containing your ARO resource. Load `state/workshop.env` below; no names or IDs need replacing. If your session expired, run `oc login -u workshop-admin`. If you changed Azure subscriptions, repeat the resource discovery in Act 0.

Capacity controls throughput, not a fixed hourly charge. Capacity `1` only allows 1 000 tokens/minute in this lab: a short curl works, but coding prompts receive HTTP 429. Allocate `500` for this single-participant run; check the model quota before sharing the endpoint with a group.

If you resize an existing deployment, https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/quota[quota changes can take up to 15 minutes to propagate]. The inference response headers `x-ratelimit-limit-tokens` and `x-ratelimit-limit-requests` show the limits currently applied; the Azure provisioning status alone does not confirm that change.

[IMPORTANT]
====
*Account and deployment provisioning usually take 1–5 minutes each.* The poller
checks every 10 seconds and permits up to 10 minutes per resource. If Azure
reports Failed/Canceled or the wait expires, stop and inspect that deployment;
do not repeat resource creation blindly. The first inference call below retries
endpoint startup errors with a 10-second delay and allows 3 minutes per attempt.
====

== Create the account and the deployment

include::ROOT:partial$run-cluster.adoc[]

[source,sh,role=execute]
----
# Load the subscription, resource group and cluster ID detected in Act 0.
source state/workshop.env
# Stop with a clear message if the resource-group discovery from Act 0 was not run.
: "${RESOURCEGROUP:?Complete the resource discovery in Act 0 first}"
# Verify access to the detected lab resource group; do not type another group ID.
az group show --name "$RESOURCEGROUP" --subscription "$SUBSCRIPTION" --output none
# Derive a lab suffix from the detected resource group.
SUFFIX="${RESOURCEGROUP#openenv-}"
# Create an alphanumeric Foundry account name unique to this lab.
FOUNDRY_NAME="$(printf 'arodeepseek%s' "$SUFFIX" | tr -cd '[:alnum:]')"
# Pin the Azure management API version used for the Foundry resource calls.
API=2025-06-01
# Use the stable deployment name later published through MaaS.
DEPLOYMENT=deepseekv4pro
# Place the external model deployment in East US 2; this does not move the ARO cluster.
LOCATION=eastus2

# Define a bounded Azure provisioning poller: check every 10 seconds, for at most 10 minutes.
wait_foundry() {
  local url=$1 state deadline=$((SECONDS + 600))
  while (( SECONDS < deadline )); do
    state=$(az rest --method get --url "$url" --query properties.provisioningState -o tsv) || return 1
    case "$state" in
      Succeeded) return 0 ;;
      Failed|Canceled) echo "Foundry provisioning: $state" >&2; return 1 ;;
    esac
    sleep 10
  done
  echo "Foundry provisioning timed out; check the Azure deployment before continuing." >&2
  return 1
}

# Create or update the declared Foundry account/deployment through Azure Resource Manager.
az rest --method put \
  --url "https://management.azure.com/subscriptions/${SUBSCRIPTION}/resourceGroups/${RESOURCEGROUP}/providers/Microsoft.CognitiveServices/accounts/${FOUNDRY_NAME}?api-version=${API}" \
  --body "{\"location\":\"${LOCATION}\",\"kind\":\"AIServices\",\"sku\":{\"name\":\"S0\"},\"properties\":{\"customSubDomainName\":\"${FOUNDRY_NAME}\",\"publicNetworkAccess\":\"Enabled\"}}" | jq .

# Wait for Azure provisioning to succeed before using the newly created resource.
wait_foundry "https://management.azure.com/subscriptions/${SUBSCRIPTION}/resourceGroups/${RESOURCEGROUP}/providers/Microsoft.CognitiveServices/accounts/${FOUNDRY_NAME}?api-version=${API}"

# List the models/version/SKU offered to this Foundry account.
az rest --method get \
  --url "https://management.azure.com/subscriptions/${SUBSCRIPTION}/resourceGroups/${RESOURCEGROUP}/providers/Microsoft.CognitiveServices/accounts/${FOUNDRY_NAME}/models?api-version=${API}" \
  --query "value[?name=='DeepSeek-V4-Pro'].{name:name,format:format,version:version,sku:skus[0].name}" -o table
----

The table should show format `DeepSeek`, version `2026-04-23`, SKU `GlobalStandard`. Then create the deployment:

== Test it

The key stays in the shell variable. Do not paste it into the chat or the workshop repo.

include::ROOT:partial$run-cluster.adoc[]

[source,sh,role=execute]
----
# Read and normalize the provider endpoint saved for the next model-publication lab.
ENDPOINT=$(az rest --method get \
  --url "https://management.azure.com/subscriptions/${SUBSCRIPTION}/resourceGroups/${RESOURCEGROUP}/providers/Microsoft.CognitiveServices/accounts/${FOUNDRY_NAME}?api-version=${API}" \
  --query "properties.endpoint" -o tsv)
# Read and normalize the provider endpoint saved for the next model-publication lab.
ENDPOINT="${ENDPOINT%/}/"
# Read the Foundry key into the shell only; do not print it or paste it into OpenCode.
KEY=$(az rest --method post \
  --url "https://management.azure.com/subscriptions/${SUBSCRIPTION}/resourceGroups/${RESOURCEGROUP}/providers/Microsoft.CognitiveServices/accounts/${FOUNDRY_NAME}/listKeys?api-version=${API}" \
  --query key1 -o tsv)

# Test the external provider directly before adding gateway and application layers.
curl --fail-with-body -sS --retry 5 --retry-all-errors --retry-delay 10 \
  --max-time 180 "${ENDPOINT}openai/v1/chat/completions" \
  -H "Content-Type: application/json" \
  -H "api-key: ${KEY}" \
  -d '{"model":"deepseekv4pro","messages":[{"role":"user","content":"Reply with one short sentence."}],"max_completion_tokens":512,"reasoning_effort":"none"}' | jq .

# Keep non-secret endpoint metadata in the ignored local state directory.
mkdir -p state
# Save only non-secret deployment metadata for Lab 1.5; the provider key is omitted.
cat > state/foundry.env << EOF
SUBSCRIPTION=${SUBSCRIPTION}
RESOURCEGROUP=${RESOURCEGROUP}
FOUNDRY_NAME=${FOUNDRY_NAME}
DEPLOYMENT=${DEPLOYMENT}
API=${API}
ENDPOINT=${ENDPOINT}
EOF
----

A new account key can take a short time to propagate; the bounded retries cover that initial delay. Persistent HTTP 401 means you should check the account endpoint/key before continuing. The answer is in `choices[0].message.content`. `state/foundry.env` has no key. Lab 1.5 reads the key again from Azure.
