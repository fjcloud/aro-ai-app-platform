= Lab 3.1 — Usage, Performance and Cost

Explore the dashboard already installed in Lab 1.3. It shows DeepSeek token
consumption through MaaS and d3-mini activity on the cluster's T4.
No additional installation or metrics commands are needed.

[NOTE]
====
*Persona:* Developer + Platform Engineer +
*Time:* 10 minutes +
*Outcome:* Identify coding versus runtime token usage and relate app activity to requests, latency and GPU utilization.
====

== Open the dashboard

. Open the *OpenShift console* using your environment's access details and sign
  in as `workshop-admin`.
. Dismiss the welcome tour if shown. Go to *Observe → Dashboards* and select
  *Workshop AI — ARO*.
. Set the time range to *Last 1 hour* and the refresh interval to *30 seconds*.
  Extend the range if you completed the earlier labs more than an hour ago.

The application generation, batch analysis and price checks from Act 2 have
already produced activity. Allow 2–3 minutes for new measurements to appear.

== Explore the existing activity

[cols="2,3",options="header"]
|===
| Look at | What to identify
| Model tokens by subscription | Compare `deepseekv4pro-workshop` (OpenCode/coding) with `deepseekv4pro-card-scout` (app/Playground research). These are cumulative totals combining input and output tokens.
| Model requests accepted by quota checks | Find the activity around generation and price checks. An accepted request is not necessarily a successful model completion.
| Quota rejections (HTTP 429) | Check whether MaaS rejected requests. Zero rejections is normal; no quota test is required. Foundry has a separate tokens-per-minute limit.
| D3 completed scoring requests / request latency p95 / queued requests | Find the batch-analysis activity. D3 scores images rather than generating text tokens; latency can be empty when no requests completed in the recent window.
| T4 utilization / memory | Compare the batch activity with quieter periods. Model memory remains allocated while idle. DeepSeek runs on Foundry, so a coding request does not use this T4.
| Scrape health | `1` means the monitoring target is reachable. A missing series or `0` needs investigation.
|===

== Connect an app action to the graphs

. Keep the dashboard open in one tab and *Card Scout* in another.
. Choose an analyzed Pokémon card whose price you have not checked yet and click
  *Check price*. Note the time.
. After the next scrapes, find the increase for `deepseekv4pro-card-scout` in the
  token and request panels. The coding subscription should not increase because
  of this action.
. Compare with the T4 panels: price research uses DeepSeek and the MCP tool,
  while D3 was used earlier for image classification.

Completed analysis and successful price research are cached. Reopening saved
results does not generate another inference request. A short request may also
fall between GPU samples; low utilization alone does not mean it never ran.

== Understand the limits and cost

In *OpenShift AI → Settings → MaaS governance*, find the coding and runtime
subscriptions. Their allowances are ten million and one million tokens per
24 hours respectively. They govern consumption, not spending caps; the shared
coding key reports workshop-level usage rather than individual participants.

The dashboard is not an Azure invoice. Its token total does not separate input,
cached input and output rates. Foundry token pricing comes from your Azure
agreement; the T4 VM, CPU workers and disks remain provisioned while idle.
