= Lab 3.1 — Usage, Performance and Cost

You have two model paths. Observe them separately, then relate activity to cost: *DeepSeek* consumes Foundry tokens through MaaS; *Whisper* uses the T4 inside ARO. An OpenCode prompt does not use the T4.

[NOTE]
====
*Time:* ~15 minutes +
*Personas:* Platform Engineer + Developer +
*Outcome:* Read actual usage, quota rejections, speech latency and GPU activity.
====

== Where to look

[cols="1,2",options="header"]
|===
| View | What it answers
| OpenShift console → *Observe → Dashboards → Workshop AI — ARO*
| How many coding tokens and requests passed through MaaS? Were requests rate-limited? How is Whisper performing?
| OpenShift AI → *Observe & monitor → Dashboard*
| Native platform health and the available model dashboards. For this workshop’s external coding endpoint and speech model, use *Workshop AI — ARO* for the verified usage and inference graphs.
| OpenShift AI → *Settings → MaaS governance*
| Which model, group and token allowance does `deepseekv4pro-workshop` permit?
| Azure Cost Management / Foundry metrics
| What did the cloud provider record and charge? Platform graphs are usage indicators, not an invoice.
|===

Lab 1.1 installs Cluster Observability Operator and OpenTelemetry, enables the native OpenShift AI metrics stack, and configures MaaS telemetry. Lab 1.4 adds a ServiceMonitor for Whisper. Metrics are collected before you reach this lab; no laptop tools or separate Grafana installation are needed. Native OpenShift AI panels depend on the serving mode and metric labels: an empty LLM-oriented panel does not establish that the external endpoint or Whisper is unavailable.

== Step 1: Create activity you can recognize

In the *Dev Spaces terminal*, make one coding request. The injected key is a MaaS key; keep it out of source and logs.

[source,sh,role=execute]
----
curl --fail-with-body -sS --max-time 180 \
  -o /tmp/workshop-coding-response.json \
  -w 'HTTP %{http_code} — request took %{time_total}s\n' \
  "${OPENAI_BASE_URL}/chat/completions" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"deepseekv4pro","messages":[{"role":"user","content":"Explain our two model paths in one short sentence."}],"max_completion_tokens":256}'
python3 -c 'import json; print(json.load(open("/tmp/workshop-coding-response.json"))["usage"])'
----

Record the input and output tokens and the request duration. The duration includes network, gateway and provider processing; it is not time-to-first-token.

Next, open *Live Transcript*, select English or French, and speak for 10–15 seconds. Confirm text appears before Stop, then stop the microphone. This creates speech requests in `speech-serving`, independently of the coding request.

Wait 2–3 minutes for configuration propagation and scraping on a fresh lab. Use the *last hour* in dashboards. A quiet GPU or zero request rate is valid when no request is running. A latency percentile needs recent completions; other empty graphs need a collection or time-range check.

== Step 2: Read coding consumption and quota

Open the OpenShift console in *Administrator* → *Observe → Dashboards* → *Workshop AI — ARO*.

* *Coding tokens by subscription*: input plus output tokens reported through MaaS, labelled `deepseekv4pro-workshop` / `deepseekv4pro`.
* *Coding requests accepted by quota checks*: requests allowed by the quota policy. This is not a count of successful completions: an upstream request can still fail.
* *Quota rejections (HTTP 429)*: attempts rejected by the model’s MaaS quota checks. Zero means no rejection has been recorded; also check scrape health.

The workshop injects one shared coding key. Its metrics represent aggregate workshop usage, not individual participant attribution. Individual showback requires individual identities/keys and the corresponding telemetry dimensions. User/group labels are disabled in this lab.

In OpenShift AI, open *Settings → MaaS governance → deepseekv4pro-workshop*. The allowance is *5 million tokens per 24 hours*. This is separate from Foundry’s tokens-per-minute quota. A MaaS allowance is not a financial spending cap; enforcement is asynchronous and in-flight calls can overshoot.

The facilitator can demonstrate a 429 without reducing the real workshop allowance:

[source,sh,role=execute]
----
# Bastion terminal, from the workshop repository.
python3 e2e/maas-quota.py
----

This test creates its own one-token subscription and a short-lived key, checks for HTTP 429, then revokes/deletes its test resources. It leaves `deepseekv4pro-workshop` available. Select a recent time window to see the quota-rejection counter change.

== Step 3: Read speech activity and latency

In the same *Workshop AI — ARO* dashboard:

* *Whisper completed requests* increases when the Go backend transcribes clips.
* *Whisper inference latency p95* measures model-side request duration. It excludes browser capture time and the app’s queue. A five-minute window with no completed requests has no latency percentile.
* *Whisper queued requests* indicates pressure on the single model replica.
* *T4 utilization* and *T4 memory used* belong to Whisper. Model memory can remain allocated while utilization is zero; short clips can finish between GPU scrapes.

Compare the graphs with your two actions: the coding request increments MaaS usage; microphone transcription increments Whisper requests. T4 memory is not DeepSeek’s model memory.

== Step 4: Check a metric directly

In *Observe → Metrics*, run one expression at a time:

[source,promql]
----
sum by (model, subscription) (authorized_hits{model="deepseekv4pro",subscription="deepseekv4pro-workshop"})
----

This is the coding token counter. On the tested Connectivity Link version its name is `authorized_hits`, without `_total`. It is a cumulative counter, not the remaining balance of a rolling 24-hour quota.

[source,promql]
----
sum(limited_calls{limitador_namespace="llm-serving/deepseekv4pro"}) or vector(0)
----

This is the model’s MaaS quota-rejection counter. A Foundry-side 429 is a separate provider limit; inspect both the MaaS allowance and Azure limits when diagnosing it.

[source,promql]
----
histogram_quantile(0.95, sum by (le) (rate(vllm:e2e_request_latency_seconds_bucket{namespace="speech-serving"}[5m])))
----

This is Whisper’s model-side p95 in seconds. Whisper decoder tokens are not Foundry coding tokens and must not be priced at the Foundry rate.

If a graph is empty, first confirm collection:

[source,promql]
----
up{namespace="speech-serving",service="whisper-predictor"}
----

Expect `1`. `0` means the target was found but could not be scraped. No series means collection is not established, or the selected time window predates the model. Check model readiness and the ServiceMonitor before blaming low utilization.

== Step 5: Relate usage to cost

Example list rates checked on *22 October 2026*, Global Standard, East US 2; these are dated estimates, not an account quote. Check the current https://prices.azure.com/api/retail/prices?$filter=productName%20eq%20%27Azure%20Deepseek%20Models%27%20and%20armRegionName%20eq%20%27eastus2%27[Azure Retail Prices API] and your agreement before pricing a session.

[cols="1,1",options="header"]
|===
| Coding meter | USD per million tokens
| Input | $1.74
| Cached input | $0.145
| Output, including reasoning | $3.48
|===

[source,text]
----
uncached_input = prompt_tokens - cached_input_tokens
dollars = uncached_input / 1_000_000 * 1.74
        + cached_input_tokens / 1_000_000 * 0.145
        + completion_tokens / 1_000_000 * 3.48
----

Use `usage.prompt_tokens_details.cached_tokens` when provided, otherwise use zero for the estimate. Do not add reasoning tokens again if already included in `completion_tokens`. The MaaS total-token counter alone cannot distinguish input, cached input and output: keep the response usage details for this calculation.

The other cost is provisioned infrastructure: the T4 VM, CPU workers, ARO worker charges and disks. They remain provisioned when the graphs are quiet. GPU watts and utilization are operational measurements, not Azure billing meters.
