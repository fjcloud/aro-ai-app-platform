= Lab 3.1 — Usage, Performance and Cost

Observe two different model paths: DeepSeek consumes Foundry tokens through MaaS; d3-mini scores news on the cluster's T4. A coding prompt or index-research request does not run DeepSeek on the T4.

[NOTE]
====
*Persona:* Developer + Platform Engineer +
*Time:* 15 minutes +
*Outcome:* Distinguish coding/runtime tokens, quota rejections, local scoring latency and GPU activity.
====

== Create recognizable activity

In the *Dev Spaces terminal*, make a short coding request:

[source,sh,role=execute]
----
curl --fail-with-body -sS --max-time 180 \
  "${OPENAI_BASE_URL}/chat/completions" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"deepseekv4pro","messages":[{"role":"user","content":"Explain relevance versus investment return in one sentence."}],"max_completion_tokens":256,"reasoning_effort":"none"}' | \
  jq '{model,usage,answer:.choices[0].message.content}'
----

Next, in *Signal Desk*, load/rank the news or change the memo to generate D3 activity. Open one story and click *Find index ideas* to generate runtime agent traffic. Record the time of each action. Reusing a cached score or idea creates no new inference request.

Wait 2–3 minutes for scraping on a fresh lab. Use *last hour* in the OpenShift console's *Observe → Dashboards → Workshop AI — ARO*. Lab 1.1 enabled MaaS telemetry and Lab 1.6 added the D3 ServiceMonitor; no separate Grafana is needed.

== Read the dashboard

[cols="2,3",options="header"]
|===
| Panel | Interpretation
| Model tokens by subscription | `deepseekv4pro-workshop` is OpenCode/coding; `deepseekv4pro-signal-desk` is app/Playground research. Input and output tokens are aggregated.
| Model requests accepted by quota checks | Allowed requests, not necessarily successful completions.
| Quota rejections (HTTP 429) | MaaS quota rejections; Foundry's separate tokens-per-minute quota may also reject calls.
| D3 completed scoring requests | Successful native `/v1/systemone` requests, not generated text tokens.
| D3 request latency p95 | Model-service request duration; no completion in the window means no percentile.
| D3 queued requests | Jobs waiting for the local model.
| T4 utilization / memory | The local decision model's GPU activity. Memory stays allocated while idle.
| Scrape health | `1` means reachable; absent series and `0` must not be described as healthy.
|===

The coding subscription permits five million tokens/24h; the separate runtime subscription permits one million/24h. These asynchronous allowances govern consumption, not spending caps. OpenShift AI's *Settings → MaaS governance* shows the model, subscription and allowance. The shared coding key gives workshop-level usage rather than individual participant attribution.

The facilitator can demonstrate a rejection from a temporary one-token subscription without lowering the real allowance:

[source,sh,role=execute]
----
# Bastion terminal, workshop checkout
python3 e2e/maas-quota.py
----

== Query the measurements directly

In *Observe → Metrics*:

[source,promql]
----
sum by (model, subscription) (authorized_hits{model="deepseekv4pro",subscription=~"deepseekv4pro-(workshop|signal-desk)"})
----

This is cumulative token usage, not remaining balance or a provider invoice.

[source,promql]
----
histogram_quantile(0.95, sum by (le) (rate(vllm_srun_request_duration_seconds_bucket{namespace="decision-serving",exported_endpoint="/v1/systemone"}[5m])))
----

This is D3 request latency in seconds. Prometheus uses `endpoint=http` for the scrape target, so the runtime’s original endpoint label is collected as `exported_endpoint`. The native runtime exports `vllm_srun_*`, not the `vllm:*` generation metrics of a vLLM Chat Completions server.

[source,promql]
----
up{namespace="decision-serving",service="d3-mini"}
----

Expect `1`. A quiet GPU is normal when idle; an absent scrape target needs investigation. A low utilization sample does not prove that a short request did not run.

From the bastion, validate all dashboard queries without printing credentials:

[source,sh,role=execute]
----
python3 e2e/check-observability.py | jq .
----

== Step 5: Relate usage to cost

Example list rates checked on *22 October 2026*, Global Standard, East US 2; these are dated estimates, not an account quote. Check the current https://prices.azure.com/api/retail/prices?$filter=productName%20eq%20%27Azure%20Deepseek%20Models%27%20and%20armRegionName%20eq%20%27eastus2%27[Azure Retail Prices API] and your agreement before pricing a session.

[cols="1,1",options="header"]
|===
| Coding meter | USD per million tokens
| Input | $1.74
| Cached input | $0.145
| Output, including reasoning | $3.48
|===

[source,text]
----
uncached_input = prompt_tokens - cached_input_tokens
dollars = uncached_input / 1_000_000 * 1.74
        + cached_input_tokens / 1_000_000 * 0.145
        + completion_tokens / 1_000_000 * 3.48
----

Use `usage.prompt_tokens_details.cached_tokens` when provided, otherwise use zero for the estimate. Do not add reasoning tokens again if already included in `completion_tokens`. The MaaS total-token counter alone cannot distinguish input, cached input and output: keep the response usage details for this calculation.

The other cost is provisioned infrastructure: the T4 VM, CPU workers, ARO worker charges and disks. They remain provisioned when the graphs are quiet. GPU watts and utilization are operational measurements, not Azure billing meters.

== Checkpoint

You can distinguish relevance-scoring requests, coding/runtime token usage, quota acceptance and GPU cost. An idle T4 still incurs VM charges; MaaS counters are not an Azure invoice.
